The Configuration tab is the main place in the UI for checking whether `ghqc` has access to a configuration repository.
It gives a lightweight overview of the pieces of configuration that affect the rest of the app, especially checklists and the active repository options,
and an easy way to set-up the configuration.

## What Configuration Controls

At a high level, the configuration repository provides the shared review setup used across `ghqc` by you or your group.
In the UI, the Configuration tab surfaces the most immediately useful parts of that setup:

- whether the configuration repository is connected
- whether it has fallen behind its remote, and a one-click way to catch it up
- which checklists are available
- how checklists are named in the UI
- whether collaborator detection is enabled for issue creation
- where key assets such as the logo and record output paths are expected
- what repository refresh interval the UI is using
- which local configuration directory `ghqc` resolved for the current session

The tab is primarily for setup and inspection. It does not expose every configuration capability directly in the UI.

## Tab Warning State

If the configuration repository has not been set up, the **Configuration** tab itself shows a warning badge and tooltip:

`Configuration repository is not set up`

This makes it visible from anywhere in the app that the shared checklist/configuration layer still needs attention.

### Stale Configuration Warning

The same yellow badge and tooltip also fire when the configuration repository *is* set up but has fallen out of sync with its remote.
This exists because a silently stale configuration is easy to miss: your checklists quietly differ from your colleagues' and nothing else in the app complains.

When the configuration repository is `behind`, the tooltip reads:

`Configuration repository is 3 commits behind org/ghqc-config. Your checklists may be out of date — update it on the Configuration tab.`

When it has `diverged`, the tooltip reads:

`Configuration repository has diverged from its remote (1 ahead, 3 behind). Resolve it manually — see the Configuration tab.`

The commit counts are live, and the repository is named as `owner/repo`.
An `ahead` state does not raise the badge — local commits that have not been pushed do not make your checklists stale.

:::note[Suppressed for centrally-managed deployments]
When updates are disabled for the deployment (`allow_ui_config_update: false` in `options.yaml`, or `GHQC_ALLOW_CONFIG_UPDATE=false`), the staleness badge is **not** shown in the nav.
There is nothing the user can do about it from there, so the signal would only be noise.
The stale state is still reported inside the Configuration tab, pointing at the administrator.

The not-set-up warning is unaffected: it always fires, regardless of whether updates are allowed.
:::

## Layout

The Configuration tab has two layers:

- an always-visible **status strip** at the very top, shown once a configuration repository is connected
- collapsible sections below it:
  - **Git Repository** — only when no configuration repository is connected yet
  - **Checklists**
  - **Options**

Each collapsible section can be expanded or collapsed independently.
The status strip is not collapsible, by design: it is the one piece of configuration state that must not be hidden behind a click.

## Git Repository

Repository state is presented in one of two ways depending on whether configuration has already been set up: a setup form in a collapsible **Git Repository** section, or the always-visible status strip.

### Not Yet Configured

When no configuration repository is connected, the section shows a setup form with:

- a **Git URL** input
- a **Set Up** button

The button remains disabled until a URL is available.

:::note[Non-Git Directory]
When pointing to an existing, non-git directory, the Git Repository section will indicate **Not a git repository** and list the directory.

This is especially import when using `GHQC_CONFIG_DIR`.
:::

### Configured State

Once configuration is available, the collapsible **Git Repository** section is replaced entirely by a status strip pinned to the top of the tab, above the **Checklists** and **Options** sections.
The strip is always visible — there is nothing to expand — so a stale configuration repository cannot be missed.

The strip shows:

- repository `owner / repo`
- a colored status pill: `clean`, `ahead`, `behind`, or `diverged`
- a **refresh** control for re-checking the repository, with the tooltip `Re-check the configuration repository`
- an **Update** button (see below)
- the human-readable status detail, e.g. `Repository is behind by 3 commits`
- the local configuration directory path, in monospace
- `Dirty: <files>` when the configuration repository has uncommitted changes

The strip's left border and background tint take the status color, so a repository that needs attention is visible at a glance.
The displayed directory is the fully resolved config location, so it reflects custom resolution sources such as `GHQC_CONFIG_DIR` when that env var is being used.

### The Update Button

**Update** performs the same fast-forward-only operation as [`ghqc configuration update`](../cli/configuration/update): it fetches the remote and runs `git pull --ff-only`, then reloads checklists.
It never merges, stashes, or leaves conflicts, and it refuses under exactly the same conditions as the CLI.

On success the strip reports:

`Configuration repository updated`

Because the checklists are reloaded, the **Checklists** and **Options** sections refresh in place — no page reload needed.
If the update is refused or fails, the error message from the server is shown in red inside the strip, using the same wording as the CLI.

**Enabled** only when the repository is `behind` — that is the one state a fast-forward can fix.

**Disabled**, with a tooltip explaining why, in every other state:

| Situation | Tooltip |
|---|---|
| Uncommitted changes present | `The configuration repository has uncommitted changes. Commit or discard them before updating.` |
| Status `clean` | `The configuration repository is already up to date.` |
| Status `ahead` | `The configuration repository has local commits that are not on the remote. Push them before updating.` |
| Status `diverged` | `The configuration repository has diverged from its remote. Resolve it manually with git.` |

The dirty-files check takes precedence: uncommitted changes block the update regardless of sync state.

**Absent entirely** when updates are disabled for the deployment via `allow_ui_config_update: false` in `options.yaml` or `GHQC_ALLOW_CONFIG_UPDATE=false`.
No disabled button is rendered — a disabled control would only invite a hunt for how to enable it.
In its place, the strip shows muted text:

`Updates are managed centrally for this deployment.`

If the repository is also `behind` or `diverged` in that case, the strip adds a yellow line so the staleness is still explained:

`Your checklists may be out of date. This deployment's configuration is managed centrally — contact your administrator.`

### Refresh Control

The refresh icon next to the status pill re-checks the configuration repository on demand, showing a loading state while the request is in flight.
Use it after pushing a change to the configuration repository from elsewhere, to confirm the UI now sees the new commits.

## Checklists

The **Checklists** section displays the checklists loaded from the configuration repository.

The layout has two parts:

- a list of checklist names on the left
- the selected checklist's content on the right in a read-only text area

The UI filters out the special `Custom` checklist from this list. Only repository-backed checklists are shown here.

If no checklists are found, the section shows:

`No checklists found`

This section is useful for quickly confirming:

- which checklist templates are available
- whether the expected checklist content was loaded
- how those templates will appear elsewhere in the app

## Options

The **Options** section displays the active repository options that `ghqc` resolved for the current session.
These are the values currently being applied, not an editor for changing them in place.

The section shows:

- **Display name** — the configured human-readable checklist name
- **Include collaborators** — whether create flows derive and expose collaborator metadata from Git history
- **Checklist directory** — where checklist files are expected inside the config repo
- **Logo path** — the configured logo location, plus whether the file was found
- **Record path** — the configured records directory
- **UI repo refresh rate** — the repository refresh interval used by the web UI
- **Allow updates from UI** — whether this deployment permits updating the configuration repository from the web UI
- **Checklist note** — the prepended checklist note, or `Not set` when none is configured

Every option is listed, so this section is a complete picture of what the application resolved. These values are read-only status information, not an editor for changing the configuration in place.

:::note[Allow updates from UI]
This row is the resolved value of `allow_ui_config_update` in `options.yaml`, or the `GHQC_ALLOW_CONFIG_UPDATE` environment variable, defaulting to **Yes**.

When it reads **No**, the **Update** button is not rendered in the status strip and the nav tab raises no staleness badge. This row is therefore where you confirm *why* those controls are absent instead of guessing. `ghqc sitrep` reports the same value as `Allow Config Update From UI`.
:::

### Display Name Behavior

The configured checklist display name affects terminology elsewhere in the UI.

For example, if the configuration uses a different display name than "Checklist", that label is reused in places like:

- Create
- Record
- other checklist-related labels throughout the app

The Configuration tab is where you can confirm which naming convention the UI is currently using.

### Include Collaborators Behavior

When **Include collaborators** is enabled, the Create flow derives collaborator metadata from the selected file's Git author history and lets you review that list before issue creation.

When it is disabled, collaborator detection is skipped and the collaborator editor is hidden from the Create flow.

## When To Use This Tab

The Configuration tab is most useful when you need to:

- set up the configuration repository for the first time
- pull down configuration changes a colleague pushed, using **Update**
- confirm that the expected config repo is connected
- confirm that a custom directory override such as `GHQC_CONFIG_DIR` resolved to the expected path
- inspect whether checklist files were loaded correctly
- verify the resolved option values, paths, and refresh settings
- diagnose why configuration-driven features in other tabs are not behaving as expected
