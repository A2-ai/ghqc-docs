`ghqc` uses a separate configuration directory to hold shared review setup for a project or team.
That directory is where `ghqc` looks for checklist files, optional UI naming overrides, a logo, and a custom record template.

This page explains the configuration model at a high level.
If you want the walkthrough of the web UI tab specifically, see [Configuration feature](../../features/configuration).

## 1. Overview

### 1.1. What Configuration Is

At runtime, configuration is just a local directory that `ghqc` knows how to read.
That directory may also be a Git repository, which is the recommended setup because it makes checklist and option changes versioned, reviewable, and shareable.

In practice, most teams use a small dedicated config repo and point `ghqc` at the local clone of that repo.

### 1.2. What Lives In The Configuration Directory

The expected layout is:

<FileTree>
- \<config-dir\>/
    - checklists/
        - checklist1.txt
        - checklist2.yaml
    - logo.png
    - options.yaml
    - record.typ
</FileTree>

- `checklists/` is where repository-backed checklist files are loaded from by default
- `options.yaml` is optional and overrides defaults
- `logo.png` is the logo used in generated QC record output
- `record.typ` is the Typst template used when generating QC records

Even with no repository-backed checklists present, `ghqc` still provides a built-in `Custom` checklist as a fallback.

## 2. Directory Resolution

The configuration directory is resolved in a fixed order:

1. `--config-dir`
2. `GHQC_CONFIG_REPO`
3. `GHQC_CONFIG_DIR`
4. default XDG data path

That means:

- if you pass `--config-dir`, it wins over everything else
- if `GHQC_CONFIG_REPO` is set, it wins over `GHQC_CONFIG_DIR`
- `GHQC_CONFIG_DIR` is only used when `--config-dir` is absent and `GHQC_CONFIG_REPO` is not set
- otherwise, `ghqc` falls back to a default local directory

### 2.1. `--config-dir`

When you pass `--config-dir`, `ghqc` uses that exact directory directly.
This is the most explicit option and the best choice for one-off runs, testing, or scripting.

### 2.2. `GHQC_CONFIG_REPO`

When `GHQC_CONFIG_REPO` is set, `ghqc` derives a local directory from the repository URL instead of using the URL itself as configuration.
It resolves to:

```text
$XDG_DATA_HOME/ghqc/<repo-name>
```

For example:

```bash
export GHQC_CONFIG_REPO=https://github.com/a2-ai/ghqc.example_config_repo
```

typically resolves to:

```text
~/.local/share/ghqc/ghqc.example_config_repo
```

This is useful because:

- the config location is stable across machines
- the repo name keeps multiple config repos distinct
- the UI can pre-fill the setup form from the environment variable

### 2.3. `GHQC_CONFIG_DIR`

When `GHQC_CONFIG_DIR` is set, `ghqc` uses that directory path directly.
This is useful when:

- using a HPC where all users in a group can read the same directory
- the configuration already exists locally outside the XDG data directory
- you do not want `ghqc` to infer a path from a Git URL
- you are testing against a local non-git directory

One important detail: `GHQC_CONFIG_DIR` has lower precedence than `GHQC_CONFIG_REPO`.
If both are set, `GHQC_CONFIG_REPO` wins.

### 2.4. Default Location

If no override is provided, `ghqc` falls back to:

```text
$XDG_DATA_HOME/ghqc/config
```

On a typical Linux or macOS setup using XDG defaults, that is often:

```text
~/.local/share/ghqc/config
```

## 3. Operation

### 3.1. Git And Non-Git Directories

`ghqc` can read configuration from either:

- a Git-backed directory
- a plain local directory

The difference is operational, not conceptual.
If the directory is a Git repo, `ghqc` can show repo details and sync status in the UI and CLI.
If it is just a local folder, configuration can still load, but setup and status information are more limited.

If setup targets an existing directory that is not already a Git repository, `ghqc` treats that as a conflict instead of silently overwriting it.

### 3.2. Recommended Setup

For most teams, the best setup is:

1. create a dedicated Git repo for configuration
2. set `GHQC_CONFIG_REPO` to that repo URL
3. run configuration setup once so the repo is cloned locally
4. keep checklists and options version-controlled there

This gives you:

- one shared source of truth for checklists
- a predictable local path on every machine
- easy inspection in the Configuration tab
- normal Git workflows for changes to review policy or templates

Use `GHQC_CONFIG_DIR` mainly for local development, experimentation, or situations where the configuration is intentionally not backed by a Git remote.

:::note[HPC]
For groups using a shared HPC, it is recommended to set `GHQC_CONFIG_DIR` to a shared, readable location.
The group's admin can then set up one configuration directory for use by all users, ensuring every user has the most up to date configuration.
:::

### 3.3. Environment Variables

The main environment variables are:

| Variable | Meaning |
|---|---|
| `GHQC_CONFIG_REPO` | Git URL used to derive the local config directory and pre-fill UI setup |
| `GHQC_CONFIG_DIR` | Explicit local directory override when no higher-precedence source is present |
| `XDG_DATA_HOME` | Base location used when `ghqc` builds its default config path |

`GHQC_CONFIG_REPO` and `GHQC_CONFIG_DIR` affect where configuration is found.
`XDG_DATA_HOME` affects where the default or repo-derived local directory lives.

### 3.4. How The UI Fits In

The Configuration tab is an inspector and setup surface for this model.
It does not define configuration behavior itself.

The tab mainly shows:

- which local directory was resolved
- whether that directory is a Git repo
- which checklists were loaded
- which option values were resolved

So the concept is: configuration is resolved first, then the UI reports what `ghqc` found.
